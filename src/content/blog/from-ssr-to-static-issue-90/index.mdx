เว็บที่คุณกำลังอ่านอยู่นี้ ถูกสร้างขึ้นมาเพื่อเป็นบันทึกของ developer คนหนึ่ง ดังนั้นเมื่อมันมีบั๊กที่ตัวมันเอง การแก้บั๊กก็ควรถูกบันทึกไว้ด้วยเช่นกัน

บทความนี้คือเรื่องราวของ [issue #90](https://github.com/suradet-ps/rxdevman/issues/90) และ [PR #119](https://github.com/suradet-ps/rxdevman/pull/119) ตั้งแต่ตอนที่สังเกตเห็นว่ามีอะไรผิด ไปจนถึงตอนที่ตรวจสอบผลลัพธ์ด้วย build จริง ถ้าคุณกำลังทำเว็บด้วย Astro แล้วขีดเส้นแบ่งระหว่าง static กับ dynamic ไม่ชัดเจน บันทึกนี้เขียนไว้เพื่อคุณ

## อาการ: README พูดอย่าง โค้ดทำอีกอย่าง

ทุกอย่างเริ่มจากคำถามง่าย ๆ ว่า บทความในเว็บนี้จริง ๆ แล้วถูก generate เป็นไฟล์ HTML ตั้งแต่ตอน build หรือเปล่า เพราะ README ของโปรเจกต์เขียนไว้ชัดเจนว่า

> rendered with zero JS by default, searchable offline

แต่เมื่อเปิดโฟลเดอร์ build ดูกลับเจอแบบนี้

```text
dist/client/blog/
├── categories/
├── index.html
├── series/
└── tags/
```

ไม่มีโฟลเดอร์ของบทความสักชิ้น ทั้งที่ในเว็บมีบทความอยู่ 27 ชิ้น นี่คือสัญญาณแรกว่าคำโฆษณากับความจริงไม่ตรงกัน

ตามมาด้วยหลักฐานอีกสองชิ้น

- `sitemap-0.xml` มีแต่ URL ของหน้า listing ไม่มีบทความเลย
- ดัชนี Pagefind ค้นไม่เจอเนื้อหาบทความ มีแต่หน้า listing กับหน้า tools

สำหรับเว็บที่เป็น knowledge base ปัญหานี้ร้ายกว่าที่คิด เพราะเว็บแบบนี้มีคุณค่าเพราะ "คนหาสิ่งที่เราเคยเขียนเจอ" ถ้า Google มองไม่เห็น และช่องค้นหาค้นไม่เจอ เนื้อหาทั้งหมดก็เท่ากับถูกฝังอยู่ใต้พรม

## ปูพื้นก่อน: Astro render ได้สองแบบ

Astro ที่ติด adapter อย่าง `@astrojs/vercel` จะทำงานแบบ hybrid ได้ คือเลือกได้ทีละหน้าว่าจะ render ตอนไหน

<InfoBox title="SSG กับ SSR ต่างกันตรงไหน">
**Static (SSG)** คือการ generate HTML จริงตั้งแต่ตอน `astro build` ลงโฟลเดอร์ `dist/client/` ผู้ใช้โหลดไฟล์ตรงจาก CDN ได้เลย เร็วและ cache ง่าย

**SSR** คือการ render HTML ตอนมี request เข้ามาถึง ผ่าน serverless function ทำให้ได้ข้อมูลสดใหม่ทุกครั้ง แต่แลกมาด้วยเวลา, ค่า server และการ cache ที่ยากขึ้น
</InfoBox>

ค่าเริ่มต้นของหน้าใน Astro คือ static ถ้าหน้าไหนอยากเป็น SSR ต้องประกาศเองว่า

```astro
export const prerender = false;
```

และนั่นคือสิ่งที่สองไฟล์นี้ทำ

```astro
// src/pages/blog/[...slug].astro
export const prerender = false;

// src/pages/index.astro
export const prerender = false;
```

ทุกบทความและหน้าแรกจึงกลายเป็น SSR โดยที่ไม่มีไฟล์ HTML อยู่ใน build เลย

## รากของปัญหา: view counter ที่อ่านตอน render

คำถามต่อมาคือ แล้วทำไมถึงต้องปิด prerender ตั้งแต่แรก

คำตอบอยู่ใน `ViewCounter.astro` เวอร์ชันเดิม ซึ่งอ่านยอดวิวจาก Supabase ด้วย service role key ตอน render

```astro
---
const { data } = await getSupabaseServer()
  .from('rxdevman_view_counts')
  .select('unique_visitors')
  .eq('page_slug', slug)
  .single();
---
```

เพื่อให้ตัวเลขถูกฝังลง HTML ตั้งแต่ first paint หน้านั้นจึงต้อง render ตอน request อ่าน database สด ๆ และเพื่อตัวเลขตัวเดียว หน้าแรกกับบทความทั้ง 27 ชิ้นก็ต้องกลายเป็น SSR ไปด้วย

ที่น่าเจ็บกว่านั้นคือ ตัวเลขก็ยัง stale อยู่ดี เพราะ script ฝั่ง client แค่ POST ไปที่ `/api/track` แล้วไม่เอาเลขใหม่ไปอัปเดต DOM คนแรกที่เข้าชมจึงเห็นเลขก่อนหน้าเสมอ แล้ว refresh อีกทีก็บวกอีกครั้ง ปัญหาส่วนนี้ถูกแยกไปติดตามใน issue #114 ต่างหาก

<SideNote type="note">
จุดนี้เป็นบทเรียนเรื่องต้นทุนของการเลือกสถาปัตยกรรม สิ่งที่ดูเหมือน "แค่ทำหน้าเป็น dynamic" จริง ๆ แล้วลากทั้งเว็บออกจาก CDN ไปผูกกับ serverless function โดยไม่จำเป็น
</SideNote>

## แก้อย่างไรใน PR #119

เป้าหมายของการแก้คือ กลับด้านทั้งสมการ ทำให้ทุกหน้าเป็น static แล้วย้ายส่วน dynamic เพียงจุดเดียวไปไว้ฝั่ง client

### 1. ให้บทความ generate ตัวเองตอน build

เปลี่ยน `[...slug].astro` ให้ประกาศ `getStaticPaths()` เพื่อบอก Astro ว่ามีหน้าไหนบ้างที่ต้องสร้าง และส่งข้อมูลโพสต์ผ่าน props แทนการค้นหาเองตอน request

```astro
export async function getStaticPaths() {
  const posts = await getCollection('blog');
  return posts.map(post => ({
    params: { slug: getEntrySlug(post.id) },
    props: { post },
  }));
}

const { post } = Astro.props;
const { Content, headings } = await render(post);
```

slug ที่ได้ยังเป็นค่าเดิมทั้งหมด เพราะใช้ `getEntrySlug(post.id)` ตัวเดียวกับที่เวอร์ชัน SSR ใช้ค้นหา URL จึงไม่เปลี่ยน ไม่มี redirect และไม่ต้องแก้ลิงก์เก่า

### 2. ย้ายการอ่านยอดวิวไปฝั่ง client

`ViewCounter.astro` เปลี่ยนจากอ่าน database ตอน render เป็นเรนเดอร์เลข 0 ไว้ก่อน แล้วค่อย hydrate ทีหลังด้วย anon key ผ่าน PostgREST โดย RLS ของตาราง `rxdevman_view_counts` เปิดให้ anon อ่านค่า aggregate อยู่แล้ว

```ts
const params = new URLSearchParams({
  select: 'unique_visitors',
  page_slug: `eq.${slug}`,
  limit: '1',
});

const response = await fetch(
  `${supabaseUrl}/rest/v1/rxdevman_view_counts?${params}`,
  { headers: { apikey: supabaseAnonKey, Authorization: `Bearer ${supabaseAnonKey}` } },
);
```

ส่วน write path ยังปลอดภัยเหมือนเดิม เพราะ `/api/track` ยังเป็น SSR route ที่ใช้ service role key ฝั่ง server เท่านั้น ฝั่ง browser ได้แค่ anon key ซึ่งถูกออกแบบมาให้เปิดเผยได้อยู่แล้ว

### 3. รายละเอียดเล็ก ๆ ที่ตั้งใจ

- ใช้ `querySelectorAll` อัปเดตทุก counter บนหน้า ไม่ใช่แค่ตัวแรก
- ถ้า environment variables หาย จะข้ามการอ่านอย่างเงียบ ๆ ไม่ทำให้หน้าเว็บพัง
- ลำดับคืออ่านเลขก่อน แล้วค่อยยิง track เพื่อรักษาพฤติกรรม "เลขก่อนการเข้าชมครั้งนี้" ให้เหมือนเดิม (การบวกเลขบนจอเป็นเรื่องของ issue #114)

## ตรวจสอบด้วย build จริง ไม่ใช่ด้วยความหวัง

หลังแก้เสร็จ ผมรัน `bun run build` ใหม่ทั้งหมด แล้วเทียบของจริง

| ตัวชี้วัด | ก่อน | หลัง |
| --- | --- | --- |
| ไฟล์ HTML ของบทความใน `dist/client/blog/` | 0 | 27 |
| URL บทความใน `sitemap-0.xml` | 0 | 30 (รวมหน้า listing) |
| หน้าในดัชนี Pagefind | 114 | 142 |
| จำนวนคำในดัชนี Pagefind | 867 | 11,849 |

คำในดัชนีที่เพิ่มจากหลักร้อยเป็นหลักหมื่น คือหลักฐานตรงที่สุดว่าบทความเข้า index จริง ไม่ใช่แค่ build ผ่าน และเพื่อความแน่ใจ ผมยังเปิดไฟล์ `.pf_fragment` ของ Pagefind ดูด้วยว่ามีข้อความจากบทความอยู่ข้างในจริง

ส่วน gate อื่นผ่านครบทั้งหมด: `bun run lint`, `bun run test` (55 tests), `bunx astro check` (0 errors, 0 warnings) และ `bun run size` (1.16 kB gzipped ตาม budget)

## บทเรียนที่เจอระหว่างทาง

### Service worker ต้องไม่แตะ dev server

ระหว่างทดสอบ dev ผมเจอ HMR websocket ต่อไม่ติด พร้อม error ประหลาดว่า `Cannot read properties of undefined (reading 'send')` สืบไปสืบมากลายเป็นว่า `public/sw.js` แคชทุก same-origin request ที่ไม่ใช่ HTML แบบ CacheFirst ซึ่งรวม `/@vite/client` ของ Vite dev server เข้าไปด้วย ทั้งที่ response นั้นส่ง `Cache-Control: no-cache` มาแล้วแท้ ๆ แต่ service worker ไม่สนใจ มันคืนสำเนาเก่าให้เบราว์เซอร์

ผลคือ browser รัน Vite client เวอร์ชันเก่า แล้ว HMR ก็พัง นี่คือตัวอย่างว่าทำไม service worker ต้องลงทะเบียนเฉพาะ production และต้องมีข้อยกเว้นสำหรับ path ของ dev (`/@vite`, `/@fs`, `/node_modules`) เรื่องนี้กำลังถูกติดตามใน issue #104

### สิ่งที่ย้ายไป client ต้องมี environment variables ตอน build

การอ่านยอดวิวแบบใหม่ใช้ `PUBLIC_SUPABASE_URL` และ `PUBLIC_SUPABASE_ANON_KEY` ซึ่ง Vite จะ inline ลง HTML ตอน build ถ้า Vercel ไม่มีค่าเหล่านี้ ตัวเลขจะกลายเป็น 0 เงียบ ๆ โดยไม่ error เลย บทเรียนคือ ของที่ย้ายไปฝั่ง client ต้องเช็ค env ของทุก environment ตั้งแต่ตอน build ไม่ใช่ตอน runtime

### CI เขียวไม่ได้แปลว่าผลลัพธ์ถูก

ทุก gate ผ่านตั้งแต่ CI ไปจนถึง CodeQL แต่ไม่มี gate ไหนรู้ว่า "บทความหายจาก sitemap" สิ่งที่จับได้คือการเปิด artifact จริงดูด้วยตา ไฟล์ที่ build ออกมาจึงควรถูกตรวจเหมือนเป็นผลผลิต ไม่ใช่แค่ผลข้างเคียง

### แยกให้ออกระหว่างโค้ดพังกับ infra หน่วง

ระหว่างรอ PR ผมเห็น Vercel preview ค้างสถานะ Building นานผิดปกติ จากสถิติเดิม deployment ของโปรเจกต์นี้ใช้เวลาไม่ถึงหนึ่งนาที ครั้งนี้ค้างเกิน 27 นาที ซึ่งไม่เกี่ยวกับโค้ดที่แก้เลย เพราะ CI build ผ่านไปแล้ว การรู้ว่า baseline ปกติคือเท่าไร ทำให้เราตัดสินใจได้ว่าควรรอ หรือควร retrigger แทนที่จะนั่งแก้โค้ดที่ไม่มีปัญหา

## สิ่งที่แยกไปทำต่อ

การแก้ครั้งนี้ตั้งใจให้ scope แคบ PR จึงจงใจไม่แตะเรื่องเหล่านี้ แต่บันทึกไว้เพื่อกลับมาทำ

- #114 view counter ยังไม่บวกเลขหลัง track สำเร็จ
- #92 build Pagefind ถูกรันซ้ำสองรอบ
- #94 ยังไม่มีหน้า 404 จริง (slug ที่ผิดจะตกไปที่ 404 ของ platform)
- #88 helper `getSupabasePublic()` ยังเป็น dead code
- #104 service worker ยังใช้ cache name คงที่และไม่ได้ป้องกัน dev HMR

## สรุป

ถ้าจะให้สรุปเป็นประโยคเดียว บันทึกนี้คือการพาเว็บกลับบ้าน กลับไปเป็น static ตามที่มันควรจะเป็นตั้งแต่แรก แล้วเก็บความ dynamic ไว้แค่จุดเดียวที่จำเป็นจริง ๆ คือตัวเลขยอดวิว ซึ่งไม่จำเป็นต้องรู้ตอน render เลยด้วยซ้ำ

สำหรับเว็บที่เป็นบันทึกของ developer การแก้บั๊กหนึ่งครั้งมักให้บทเรียนมากกว่าตัวโค้ดที่แก้ และบทเรียนที่คุ้มที่สุดของครั้งนี้คือ ประโยคใน README ควรถูกพิสูจน์ด้วย artifact ที่ build ออกมา ไม่ใช่ด้วยความตั้งใจตอนเขียน
